# Пакетная сборка пространств, статей и ТБД

Подготовь содержание и схему по навыкам `$teamly-create-space` и `$teamly-demo-articles`. Передай проверенный план сборщику, чтобы одна сессия Chrome выполнила последовательность действий. В модели остаются сценарий, подготовка материалов, проверка спорных шагов и отчёт. Для четырёх макетов суперстатьи действует [отдельный сборщик](../scripts/teamly-browser.mjs).

## Запуск

Нужны Node.js 20+, Chrome и Playwright из существующего `package-lock.json`. Из корня репозитория установи зависимости через `npm ci`, затем для команд ниже перейди в папку `teamly-superarticle`. Для отдельно установленного навыка выполни `npm ci` из его папки. Используй прежний отдельный профиль Teamly или создай отдельный профиль для этого хоста. При необходимости один раз запусти вход.

```sh
node scripts/teamly-code.mjs check /path/to/plan.json
node scripts/teamly-code.mjs sign-in /path/to/plan.json --profile /path/to/teamly-profile
node scripts/teamly-code.mjs build /path/to/plan.json --profile /path/to/teamly-profile --state /path/to/plan.state.json
node scripts/teamly-code.mjs verify /path/to/plan.json --profile /path/to/teamly-profile --state /path/to/plan.state.json
```

`check` проверяет план и файлы без запуска браузера. `build` создаёт и наполняет объекты, сверяет сохранённый результат и возвращает ключ, URL и статус. `verify` открывает существующие объекты и проверяет признаки без внесения изменений. Для проверки используй прежний файл состояния. Для команд `build` и `verify` доступен `--headless`. Неподтверждённые пункты возвращаются отдельно с причинами. Зависимые действия выполняются после подтверждения заданных зависимостей, остальные могут идти дальше.

## План

- `version: 1`. В `space` укажи текущий `url` вида `/sp/…` или подтверждённый адрес списка `list` вида `/space/list/all`, точное `title`, при необходимости `description` и `create: true` для явно порученного создания. Сборщик ищет совпадение через поиск пространств. Если интерфейс не показал ни точного совпадения, ни пустого результата, сверь список и укажи URL либо подтверждённый признак отсутствия в `space.absence`. В мастере можно передать UI-действия `settings` и точный контрол `finish` после проверки экрана.
- `items` перечисляет шаги по порядку. Каждый получает постоянный `key`. Родитель `parent` и цель `on` ссылаются на ранее описанный объект или `space`. `requires` принимает ключи предыдущих шагов, успешность которых нужна для этого шага. Сохраняй ключи паспорта ROOT и SEC-01…05. Для уже известного объекта укажи `url`; сборщик подтвердит его положение. Для нового объекта используй точное название в нужной ветке. Найденный объект используется повторно.
- `kind: "article"` принимает `title`, `html` с нативным содержимым редактора и список фраз `expect` для проверки. Используй содержательные фразы из разных разделов. `files` — существующие файлы, которые сборщик прикрепит через редактор. `publish: true` используй, если поручение включает публикацию. `root: true` ищет корневую статью. `populateEmpty: true` разрешает заполнить уже существующую пустую статью. Для изменения отдельных блоков существующей статьи применяй адресные шаги редактора. Статьи с содержимым проверяются и переиспользуются.
- `kind: "table"` принимает `title`, `fields` и `rows`. Для пакетного пути предусмотрены «Текст», «Число», «Выбор», «Статус», «Дата», «Исполнитель» и «ID». У поля «Выбор» можно указать `options`. Строка содержит уникальное рабочее `title` и `cells`, где ключом служит имя столбца. Число передавай числом. Для даты или любого значения, которое отображается иначе, используй `{"input":"видимая подпись элемента календаря","display":"сохранённая дата"}`. Если выбранное представление важно для проверки, сохраняй его в URL таблицы. Сверяй записи и поля в подходящем представлении с видимыми строками и столбцами. При несовпадении существующих значений сборщик указывает конфликт.
- `kind: "ui"` добавляет операции для установленного интерфейса. `on` указывает объект, `title` описывает действие, `steps` выполняет последовательность с исходной страницы объекта. `verify` проверяет сохранённый результат после повторного открытия. `before` при необходимости открывает панель для чтения. Описывай только наблюдавшиеся контролы текущей версии и проверяй конечный эффект.
- `kind: "manual"` сохраняет в отчёте требование, которое предстоит выполнить через редактор по исходной инструкции. После проверки используй подтверждённый результат для паспорта. Если подготовишь следующую редакцию плана, передай в неё подтверждённые URL.

Для обложек, эмодзи, навигации, доступа, представлений, фильтров, связей, Rollup, форм, формул, сценариев диалога, глоссария и встраиваний используй `ui` с точными контролами и проверкой или соответствующую справку навыка для продолжения в редакторе. Связь настраивай после появления обеих таблиц и записей, Rollup — после связи. Проверяй пересчёт. Для доступа используй только согласованных субъектов и уровни. Сохраняй критерии полного демохоста, матрицу покрытия и порядок из исходных навыков.

### Шаги редактора

У шага есть `do` и `target`. Цель — CSS-селектор или объект с одним из ключей `css`, `button`, `text`, `label`, `placeholder`. При необходимости добавь `within` с CSS-селектором области. Имена сопоставляются точно. Действия — `click`, `fill`, `press`, `check`, `upload`. Для ввода, клавиши и файла передай `value`. Для загрузки укажи CSS поля загрузки. Пути к файлам разрешаются относительно плана.

У проверки есть `target` и `state`. Поддерживаются `visible`, `hidden`, `text`, `value`, `checked`, `attribute` с `name` и `count`. Например, навигация проверяется по числу карточек и точным ссылкам, обложка — по сохранённой обложке и отображению карточки, фильтр — по фактической выборке. Сохраняй проверку отдельно от кликов по контролам.

## Возобновление

Оставляй тот же план, файлы и файл состояния. Сборщик запоминает URL сразу после открытия нового объекта и проверяет состояние перед повтором. Для шага с неизвестным результатом сначала сверь текущий объект, дерево и черновики. Только если действие точно не произошло, передай `--retry` с точным ключом из отчёта. Отчёт группирует однотипные ошибки и приводит до трёх примеров. Ключи начатых операций смотри в файле состояния. Ключи полей и ячеек с пробелами заключай в кавычки. При изменении плана сохрани прошлый файл состояния и перенеси в новый план проверенные URL. Если после аварийного закрытия осталась блокировка файла, сперва проверь, что сборщик завершён.

Перенеси подтверждённые ссылки, статусы и ближайший шаг в тот же паспорт демохоста. Сохраняй отдельно неподтверждённые настройки, состояние публикации и проверки, для которых нужен другой режим доступа. Итоговый отчёт основывай на результате проверки, включая действия, завершённые через редактор.

Примеры структуры: [каркас пространства](../examples/code-mode/space.json) и [статья с ТБД](../examples/code-mode/content.json). Заменяй учебный домен актуальным хостом из запроса.
